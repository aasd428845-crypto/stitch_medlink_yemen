## C. Discount UI contract (design only)

Remediation stays a sequenced follow-up, not a precondition for client discount wiring.

## E. Cancellation design (no code changed)
Current paths: client has none; branch `branch_order_actions.dart:159` → `updateOrderStatus` → direct `cancelled` write. No trigger point calls `cancel_order_discount` today. Designed link: at every order→cancelled transition, the actor (app layer, since no DB trigger exists on orders) first checks for a POSTED ORDER_DISCOUNT row for the order and, if present, calls `cancel_order_discount(p_order_id, reason, key REVERSAL:DISCOUNT:{order})` BEFORE/AFTER the status write — order between the two does not affect money safety (reversal is order-status-independent except delivered-guard), but calling before the status update keeps failure attribution clean (status stays un-cancelled if reversal raises under MANUAL snapshot). Guards preserved: POSTED original untouched (trigger-enforced), independent REVERSAL row, replay-key idempotency, one-effective-reversal (guard + `bonus_ledger_reverses_uniq`), no double-spend (credit-only compensation). If a future transaction boundary is wanted (status + reversal atomic), it requires a new RPC wrapping both — designed here as an option, not implemented; current two-call sequence with retry-safe keys is sufficient and matches the codebase's existing multi-call patterns.

## F. Idempotency design (0020 suffices — nothing invented)
Key `DISCOUNT:{order_id}` generated by RPC default (0020:70-71). App must NOT pre-generate: controller holds no key initially, passes none (server default applies), and on retry-after-timeout re-invokes with no key → same default → replay returns existing id. Success-with-lost-response resolves identically on retry. Duplicates prevented at three levels: in-RPC replay SELECT, post-lock exists-check, UNIQUE(idempotency_key). Custom keys reserved for future multi-step flows only, with the 17.2/F3 uniqueness contract.
