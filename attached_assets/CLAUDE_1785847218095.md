# MedLink Yemen — دليل السياق الرئيسي لإعادة البناء بـFlutter

## 1. نظرة عامة على المشروع
تطبيق B2B مغلق (ليس عاماً) لشركة توريد أدوية ضخمة في اليمن، تمتلك فروعاً في عدة محافظات. **هذا ليس تطبيقاً استهلاكياً عاماً** — التسجيل يمر ببوابة موافقة إلزامية من الإدارة قبل تفعيل أي حساب عميل.

النموذج التجاري: كتالوج مركزي موحد الأسعار، كل فرع له مخزون خاص بكميته فقط، العميل يطلب مباشرة ويُوجَّه تلقائياً لأقرب فرع، مدير الفرع يخصص ويوصّل عبر سائق، **التوصيل مجاني بالكامل دائماً (لا يوجد أي حقل أو حساب لرسوم توصيل في أي مكان بالتطبيق)**.

## 3. قواعد معمارية صارمة (غير قابلة للتفاوض — نتائج تجربة سابقة فاشلة مع تقنية أخرى)

1. **مصادقة Supabase حقيقية 100% من أول سطر كود.** ممنوع منعاً باتاً: أي حساب تجريبي جاهز، أي دخول بدون تحقق كلمة مرور فعلي، أي كلمة مرور موحّدة/ثابتة لعدة حسابات.
2. **لا تُدرِج أي صف يدوياً بجدول `users` بعد التسجيل.** الجدول يُملأ حصراً عبر Trigger تلقائي بقاعدة البيانات (`handle_new_user`, موجود مسبقاً). أي محاولة `insert`/`upsert` يدوية على `users` بعد التسجيل = خطأ معماري ممنوع.
3. **كل Model يمثّل جدول Supabase يجب أن يُسلسَل (Serialize) بدقة مطابقة تماماً لأسماء أعمدة snake_case الحقيقية.** استخدم `json_serializable`/`freezed` مع `@JsonKey(name: 'snake_case_name')` صريح لكل حقل، تحقق من التطابق حرفاً بحرف مع ملفات SQL المرفقة أدناه قبل أي استدعاء.
4. **لا تُولِّد أي معرّف (id) يدوياً بالكود أبداً** (لا `"prefix_" + timestamp`، لا أي نص مؤقت) — كل جداول قاعدة البيانات تستخدم `uuid default gen_random_uuid()`، اترك القاعدة تولّده دائماً.
5. **منطق كل عملية (حفظ عنوان، تسجيل طلب...) يُكتب في مكان واحد فقط (دالة/Service واحدة)، ويُستدعى من كل الشاشات التي تحتاجه.** ممنوع تكرار نفس منطق الحفظ بأكثر من ملف بطريقة مختلفة أو ناقصة.
6. **ممنوع عرض أي رسالة "تم بنجاح" قبل التأكد الفعلي من نجاح العملية بقاعدة البيانات.** كل رسالة نجاح يجب أن تكون مشروطة بنتيجة استجابة حقيقية من Supabase (لا try/catch يبتلع الخطأ ويعرض نجاحاً وهمياً).
7. **سجّل كل خطأ بوضوح** عبر `debugPrint`/`log` بوسم `SUPABASE_DEBUG` يتضمن اسم الدالة ونص الخطأ الكامل — هذا إلزامي لكل عملية اتصال بقاعدة البيانات، يسهّل التشخيص لاحقاً.
8. **الملفات الطويلة (خدمات) تُقسَّم منطقياً**: `AuthService`, `CatalogService`, `OrderService`, `InventoryService`, `DriverService`, `NotificationService` — كل واحدة بملف Dart منفصل داخل `lib/services/`، لا ملف خدمة واحد ضخم يحتوي كل شيء.
9. **بنية الترجمة (i18n) من أول شاشة تُبنى**: استخدم `flutter_localizations` + ملفات ARB (`lib/l10n/app_ar.arb`, `lib/l10n/app_en.arb`). كل نص ظاهر للمستخدم = مفتاح ترجمة، بدون استثناء، من أول شاشة.
10. **قاعدة تنفيذ الدفعات**: ابنِ ميزة واحدة مكتملة (شاشة + منطق + اتصال قاعدة بيانات حقيقي) بكل رد، لا تنتقل للتالية قبل التأكيد. بعد كل دفعة، اذكر بدقة: أي ملفات أنشأتها/عدّلتها، وهل اختبرتها فعلياً (Hot Reload) أم لا.

## 6. قائمة الشاشات الكاملة (المصدر: تصاميم Stitch المرفوعة معك بمشروع "MedLink Yemen Enterprise")

**العميل**: تسجيل دخول/حساب + Google Sign-In، موافقة الشروط وسياسة الخصوصية، شاشة "بانتظار المراجعة"، الرئيسية/الكتالوج، تفاصيل المنتج، السلة (مع منطق البونص التلقائي)، تأكيد الطلب، طلب خاص (نص أو تسجيل صوتي)، سجل الطلبات + إعادة الطلب، تفاصيل الطلب + شريط تقدّم، إعداد الملف الشخصي (قابل للتخطي)، العناوين + خريطة Google حقيقية، البطاقة الرقمية، مركز التنبيهات، تقييم السائق بعد التسليم، المساعدة والدعم، إعدادات اللغة.

**مدير الفرع**: لوحة التخصيص (تحويل يدوي/تلقائي جزئي/كامل + جدولة تسليم إلزامية)، سجل الفواتير، مخزون المستودع، إدارة حسابات السائقين، الإحصائيات والتقارير.

**السائق**: قائمة الطلبات المُسندة، تفاصيل الطلب (خرائط + اتصال + زر حالة ديناميكي)، أرباحي/عمولاتي، الدردشة المباشرة مع مدير الفرع (نص + موقع حي — **رتّبها آخر أولوية بخطة التنفيذ، أعقد ميزة بالمشروع**).

**مشترك بين الأدوار**: قائمة المحادثات، غرفة الدردشة.

## 7. منطق أعمال حرج يجب الانتباه له بدقة

- **البونص**: عند إضافة صنف للسلة، تحقق من `bonus_rules` النشطة لنفس الصنف؛ لو الكمية تحقق الشرط، أضف سطر "🎁 بونص" بسعر 0 تلقائياً، **واخصمه من المخزون الفعلي أيضاً** (ليس مجانياً على مستوى المخزون).
- **العمولات**: عند تأكيد السائق للتسليم، احسب العمولة حسب أعلى أولوية تنطبق (سائق مخصص > فرع مخصص > قاعدة عامة) من `driver_commission_rules`، وسجّلها بـ`driver_commissions` بحالة `pending`.
- **بوابة الموافقة**: أي عميل جديد `account_status = 'pending_approval'` لا يدخل الشاشة الرئيسية — يُوجَّه لشاشة الانتظار حتى يوافق المدير العام (من الويب، خارج نطاقك).
- **تحويل الطلبات**: أربعة خيارات (يدوي جزئي/كامل، ذكي تلقائي جزئي/كامل) — راجع `orders.parent_order_id` و`orders.target_branches` بملف `0002` القادم لفهم آلية التقسيم.

## 8. خطة التنفيذ المرحلية (نفّذها بهذا الترتيب بالضبط)

1. تأسيس المشروع + بنية i18n + المصادقة الحقيقية + بوابة الموافقة
2. الكتالوج + المخزون (اكتب `0002_catalog_inventory_orders.sql`)
3. السلة + الطلب المباشر + البونص + التوجيه للفرع
4. لوحة مدير الفرع كاملة (تخصيص، تحويل، فواتير، مخزون)
5. إدارة السائقين (إنشاء الحساب — راجع أنه لا يُسجِّل خروج مدير الفرع الحالي، استخدم Edge Function وليس signUp عادي)
6. واجهة السائق (الطلبات، الخرائط، أرباحي)
7. مركز التنبيهات + العروض الترويجية
8. تقييم السائق + المساعدة والدعم
9. **الدردشة الحية + الموقع الحي (آخر شيء، وبعد استقرار كل ما سبق فقط)**

## 9. طريقة معاينة الأدوار الثلاثة أثناء التطوير (سؤالك الأخير)

أبسط طريقة وأكثرها أماناً: بعد ما تُبنى شاشة التسجيل، **سجّل يدوياً 3 حسابات تجريبية حقيقية من داخل التطبيق نفسه** بإيميلات مميزة (مثال: `test.client@medlink.dev`, `test.branch@medlink.dev`, `test.driver@medlink.dev`)، ثم روح **Supabase Dashboard → Table Editor → users**، وعدّل يدوياً لكل حساب: `role` المناسب، و`account_status = 'active'` (لتفادي بوابة الموافقة أثناء اختبارك أنت)، وللسائق/مدير الفرع حدد `branch_id`. بهذي الطريقة تسجّل دخول وخروج بين الحسابات الثلاثة بحرية كاملة أثناء التطوير، دون الحاجة لأي كود اختباري إضافي بالتطبيق نفسه (وأهم شي: بدون أي "وضع تجربة" يبقى بالكود وينسى حذفه وقت الإطلاق الحقيقي — نفس الغلطة اللي وقعنا فيها بمشروع Kotlin).
